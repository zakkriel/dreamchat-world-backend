# 02 PoC Scope and Success Criteria

## Purpose

This document defines the smallest proof of concept needed to validate the product vision.

The PoC is not the full app.

The PoC is the smallest product experience that can prove whether one small world can feel persistent, remembered, and changed across in-world time.

## Core PoC Question

Can one small world remember important past events and use that memory to evolve coherently when in-world time passes?

This is the central question.

The PoC should not only prove that memory can be retrieved. It should prove that memory can support living-world continuity.

## Memory and Living-World Continuity

Memory and living-world behavior are connected, but not identical.

Memory is the foundation.

Living-world continuity is the improvement built on top of memory.

A world cannot feel alive if it cannot first remember what happened.

The PoC should therefore validate two layers.

### Layer 1: Memory Works

The world remembers important facts, relationships, commitments, context, and prior events.

Entities should preserve their identity, known context, relationship state, and knowledge boundaries across long gaps of unrelated activity.

### Layer 2: Living-World Continuity Works

Because memory is stable, the world can evolve when in-world time passes.

Entities, relationships, groups, locations, unresolved threads, and public knowledge may change in ways that feel coherent with the past.

## PoC Scope

The PoC includes:

- one world

- one user-controlled character/entity

- one narrator/facilitator

- 5–10 meaningful entities/NPCs that can be managed

- a few locations

- a visible timeline/history

- a relationship system

- memory/canon correction UX

- in-world time progression

- backstage updates

- persistent entity memory

- knowledge boundaries

## PoC World Shape

The PoC world should be a contained living-world sandbox.

It should not depend on a specific genre. It can be fantasy, political, modern, sci-fi, horror, romance, realistic, or any other style.

What matters is that it contains enough social and historical structure to test memory, relationships, knowledge boundaries, in-world time, and backstage updates.

The PoC world should include:

- 3–5 locations

- 5–10 meaningful entities/NPCs

- 2–3 active power structures

- 3–5 unresolved threads, tensions, or commitments

- a visible timeline/history

- a distinction between private knowledge, shared knowledge, and public knowledge

The PoC should prove depth, not scale.

The goal is not to simulate an entire civilization. The goal is to make one contained world feel coherent, remembered, and alive.

## Power Structure Scope

The PoC should include power structures, but only a small number should be actively simulated.

Power structures are any groups, institutions, networks, or collective forces that can affect the world.

Examples include:

- a local political office

- a neighborhood group

- a criminal organization

- a corporate department

- a research lab

- a family dynasty

- a small religious order

- a rebel cell

- a local guild chapter

- a school administration

- a private security force

The PoC should actively simulate local or contained structures first.

Large structures may exist, but they should usually appear as background pressure rather than full active simulation.

## Active Structures, Background Pressure, and Lore-Only Structures

The product should distinguish between three levels of structural depth.

### Active Structures

Active Structures are directly simulated in the current world scope.

They have named entities, relationships, goals, conflicts, memory, and backstage updates.

### Background Pressure

Background Pressure represents larger forces that influence the contained world without being fully simulated yet.

Examples include national governments, continental institutions, global corporations, distant wars, mass movements, cultural shifts, economic forces, or large religions.

These forces can create pressure through laws, rumors, prices, fear, opportunities, propaganda, social expectations, or institutional consequences.

### Lore-Only Structures

Lore-Only Structures exist as context, history, or world flavor.

They do not actively affect the current world unless promoted later.

## Promotion Rule

A structure can move from lore-only to background pressure, or from background pressure to active structure, when the user's actions or the world's evolution make it relevant.

This is not only a PoC shortcut. It is a full-product scaling principle.

Even the full product should not simulate every structure at equal depth all the time.

The product should decide what is active now, what creates pressure, what remains lore, and what should be promoted because the story touched it.

## What Is Excluded

The PoC should not include everything the final product may eventually support.

Excluded from PoC:

- marketplace

- public world publishing

- multiplayer

- full creator economy

- full rules system

- full media generation layer

- broad template library

- mobile app polish

- complex monetization UX

- advanced social/community features

The PoC should stay focused on proving the core product promise.

## Core User Journey

The PoC journey should be simple.

1. The user enters or creates one small world.

2. The user interacts with several entities/NPCs.

3. The user creates meaningful relationships, commitments, conflicts, or unresolved threads.

4. The world records what matters.

5. The user continues through many unrelated actions and events.

6. In-world time passes.

7. Previously encountered entities are reintroduced.

8. The user sees that memory, relationships, knowledge boundaries, and world changes are coherent.

## Core Validation Scenario: Long-Gap Entity Recovery

This is one of the most important PoC tests.

An entity can be created, meaningfully updated, ignored for 1,000+ unrelated actions, and later recovered with its correct identity, relationship state, known context, and knowledge boundaries intact.

### Scenario

- Action 1: Entity 1 is created.

- Action 3: Entity 1 meaningfully changes because of interaction or event.

- Actions 4-1000+: Many unrelated actions happen. These may create new events, new entities, new relationships, new world changes, and new changes to the user-controlled character/entity.

- Action 1001+: Entity 1 is reintroduced.

### Expected Result

Entity 1 should recover:

- identity

- prior relationship state

- relevant shared history

- commitments or unresolved threads

- emotional/social stance

- known context

- knowledge boundaries

Entity 1 should not automatically know unrelated events that happened after it left the relevant context.

The entity may only know those events if there is a valid in-world reason for that knowledge to reach it.

## Core Validation Scenario: Long-Running Entity Recall

This test validates a different memory risk than long-gap recovery.

The question is not whether an entity can be recovered after being absent.

The question is whether an entity that stays active across a long sequence can still remember an early topic correctly after many related actions.

### Scenario

- Action 1: Entity 1 appears.

- Action 10: Entity 1 learns or discusses an important topic.

- Actions 11-1000+: Entity 1 remains active or repeatedly involved across many related actions, changes, and interactions.

- Action 1001+: The early topic from Action 10 becomes relevant again.

### Expected Result

Entity 1 should recall the early topic correctly.

The memory should not be overwritten, diluted, contradicted, or replaced by later related events.

Later development may change the entity's interpretation of the topic, but it should not erase or distort what was originally established.

This proves that long-running continuity works for active entities, not only dormant ones.

## Core Validation Scenario: Memory Evolution Recall

This test validates memory evolution, not only memory persistence.

The entity should not only remember the latest version of a topic. It should understand that the topic changed over time.

### Scenario

- Action 1: Entity 1 appears.

- Action 10: Entity 1 learns or discusses an important topic.

- Action 200: The topic is updated, clarified, contradicted, reframed, or emotionally changed.

- Action 700: The topic is updated again.

- Action 1001+: The topic becomes relevant again.

### Expected Result

Entity 1 should recall:

- what was originally established

- what changed at Action 200

- what changed at Action 700

- what the current state is

- whether older versions still matter

This proves the product does not collapse evolving history into only the latest summary.

## Knowledge Boundary Rule

Entities should not become magically omniscient.

An entity should know:

- what it directly experienced

- what it was told

- what it inferred reasonably

- what became public knowledge

- what reached it through an information source

An entity should not automatically know:

- private user-controlled character/entity experiences

- unrelated events

- private conversations it did not witness

- changes that never reached its information context

This rule is critical for immersion.

## Core Validation Scenario: Public vs Private Knowledge

This test proves that the world does not treat all information as globally known.

The same event can exist as private knowledge for one entity, unknown knowledge for another, and later public or indirect knowledge for a third.

### Scenario

- Action 10: The user and Entity 1 discuss a private topic.

- Entity 2 is not present.

- Action 100: Entity 2 interacts with the user.

- Entity 2 should not know the private topic.

- Action 200: The topic becomes public through rumor, record, broadcast, gossip, report, or another information source.

- Action 300: Entity 2 may now know about it, but only as indirect or public knowledge.

### Expected Result

Entity 1 knows the topic as direct shared memory.

Entity 2 does not know it until there is a valid information path.

If Entity 2 learns it later, the product should preserve source, reliability, trust, bias, distortion, omissions, and uncertainty.

## Backstage Decay and Review

Backstage is not memory retrieval.

Backstage is a controlled world-state review process.

Node Decay measures how much pressure has accumulated for a node's known state to be reviewed, because after elapsed in-world time and connected world events, the node may no longer be what it could or should be.

Decay does not mean the product forgot the node.

Decay means the known current state of that node may deserve review before the world keeps using it.

### Core Rule

High decay triggers review.

High decay does not force dramatic change.

A review can conclude:

- no meaningful change

- small change

- relationship change

- knowledge update

- status change

- new dependent node

- meaningful world change, only if justified

The product should avoid random drama generation.

A node should evolve from existing relationships, known motivations, elapsed in-world time, background pressure, unresolved consequences, and world context.

## Backstage Review Triggers

The PoC should support three Backstage review triggers.

### 1. Active Trigger

An Active Trigger happens when the user shows intent to contact, visit, inspect, ask about, rely on, or investigate a world node.

Examples:

- the user wants to meet an entity

- the user asks what happened to a group or institution

- the user returns to a location

- the user checks on a relationship, rumor, or public situation

Before the interaction starts, the product should decide whether the touched node has enough decay to require Backstage review.

### 2. Passive Time-Jump Trigger

A Passive Time-Jump Trigger happens when story time clearly moves forward.

Examples:

- three months pass

- the user spends two weeks crafting, hiding, recovering, or training

- the story skips to the next season

- the user returns after an in-world year

The product should not update the entire world.

It should build a limited review queue of relevant nodes.

### 3. Passive Accumulated-Time Trigger

A Passive Accumulated-Time Trigger happens when enough in-world time has passed through normal play, even without an explicit time jump.

Example:

- from Action 10 to Action 200, three in-world months pass through scenes, travel, conversations, and events

- a highly relevant world node has not been reviewed during that elapsed story time

The trigger is not whether there was a visible time skip.

The trigger is whether enough in-world time and connected pressure accumulated since the node's last meaningful review.

## Backstage Review Queue

A Backstage trigger should create a review queue, not force the whole world to update immediately.

Candidate nodes may include:

- the node directly touched by user intent

- entities currently with the user-controlled character/entity

- the current location

- directly connected entities

- active structures

- high world-relevance structures

- high user-relevance entities

- volatile nodes

- nodes connected to recently changed nodes

- nodes under strong background pressure

The product should prioritize what needs to be reviewed now.

The PoC should prove ordered partial resolution, not global simulation.

## Review Priority

The review queue should prioritize:

1. Immediate interaction nodes.

2. Directly connected nodes that may affect the immediate interaction.

3. User-proximal nodes such as current companions, current location, and current active context.

4. High world-relevance nodes that may create background pressure.

5. Low-relevance or low-visibility nodes only when touched or strongly connected.

A major world structure may deserve lightweight review even when the user is not directly interacting with it.

But reviewing a high-world-relevance node does not mean something world-shattering must happen.

## Backstage Update Radius

Backstage propagation should be bounded.

### Radius 0

The review affects only the target node.

Example: an entity changed role, location, mood, status, or public position.

### Radius 1

The review may affect directly connected nodes.

Example: Entity 1 and Entity 2 formed a relationship, separated, had a child, entered a conflict, or changed their shared obligations.

Radius 1 can create a new node if the result is directly justified by existing context.

### Radius 2+

Radius 2+ should not automatically run in the PoC.

Wider consequences should usually become background pressure, a future hook, or an unresolved review pressure rather than an immediate cascade.

This prevents the product from turning one update into a full-world recomputation.

## Backstage Product Guardrails

The PoC should follow these guardrails:

- Backstage is based on in-world time, not real-world user absence.

- Backstage review is lazy, bounded, and priority-driven.

- Decay means review pressure, not forced change.

- A review may produce no meaningful change.

- The world should not update every node equally.

- Updates should move through valid relationships and information paths.

- Social Memory Propagation should not become omniscience.

- RAG-style retrieval may support context, but canon and world state should not be treated as chat-history recall.

- The product should avoid uncontrolled cascading updates.

## Social Memory Propagation

Social Memory Propagation is parked as a later feature, but the PoC should already respect the principle behind it.

Entities can gain knowledge indirectly through other entities or information sources.

Examples of information sources:

- another entity

- gossip

- rumors

- public records

- warrants

- newspapers

- bard tales

- social media

- letters

- broadcasts

- group reports

- institutional records

- surveillance

- local reputation

- cultural memory

- propaganda

- private testimony

Indirect knowledge is not direct memory.

If Entity 1 learns something from Entity 2, Entity 1 should know it as secondhand knowledge, with source, trust, bias, distortion, omissions, and uncertainty.

## Correction Window

The PoC should support a correction window between messages.

After a generated response, the user can correct the current moment before the next user action accepts it into history.

During this window, the user can correct things like:

- an entity was or was not present

- an entity did or did not say something

- an event did or did not happen

- a relationship state was represented incorrectly

- a piece of knowledge was assigned to the wrong entity

- the narrator made a wrong assumption

Once the next user action happens, the previous moment is treated as accepted history.

The PoC should not attempt deep retroactive correction by default.

## Present-Forward Correction Rule

If the user corrects something after the correction window has passed, the correction updates current canon and future behavior only.

It does not automatically rewrite all downstream consequences from the past.

For example, if the world wrongly believes an entity died and the user later corrects that the entity is alive, the PoC should treat the entity as alive from now forward.

It should not automatically recalculate every past consequence of the false death.

This avoids reverse butterfly-effect collapse inside the PoC.

## Memory and Canon Correction UX

The PoC must include a basic way for the user to correct world memory or canon.

Correction should not feel like debugging.

It should feel like directing the world.

The user should be able to say, in product terms:

- this happened

- this did not happen

- this entity knows this

- this entity does not know this

- this is public knowledge

- this is private knowledge

- this is rumor

- this is confirmed

- this relationship state is wrong

The correction mechanism is part of the product promise because persistent worlds will sometimes need repair.

## PoC Validation Matrix

| Test | What it proves | Pass signal |

|---|---|---|

| Long-gap entity recovery | Memory survives absence and unrelated activity | An entity can return after 1,000+ unrelated actions with identity, relationship state, known context, and knowledge boundaries intact. |

| Long-running entity recall | Memory survives heavy related activity | An active entity can recall an early topic correctly after 1,000+ related actions. |

| Memory evolution recall | Memory tracks original state plus later updates | The entity recalls what was first established, what changed later, and what the current state is. |

| Public/private knowledge | Entities do not become omniscient | Different entities preserve different knowledge states until valid information paths exist. |

| In-world time progression | Time changes the world only inside the fiction | Real-world absence does not move the world; in-world elapsed time can change relevant nodes. |

| Backstage Decay review | World nodes are reviewed when their known state may no longer be what it could or should be | High-decay nodes are reviewed, but review can produce no change, small change, or justified meaningful change. |

| Background pressure | Large forces influence the contained world without full simulation | A large structure can create laws, rumors, fear, opportunities, or social pressure without becoming fully active. |

| Bounded propagation | Backstage updates do not explode into full-world recomputation | Radius 0 and controlled Radius 1 updates work; Radius 2+ becomes pressure, hook, or future review. |

| Correction window | Current canon can be repaired safely | The user can correct the current moment before it is accepted into history. |

| Present-forward correction | Late corrections avoid reverse butterfly-effect collapse | After the correction window, corrections affect current canon and future behavior, not automatic past rewrites. |

| Timeline/history usefulness | The world history is visible and useful | The user can understand what happened, what changed, when it changed, and why it matters. |

## Success Criteria

The PoC succeeds if a user can believe that one small world has continuity.

Specific success criteria:

- The world remembers important prior events.

- Entities recover correctly after long gaps of unrelated actions.

- Entities preserve knowledge boundaries.

- Relationships remain coherent over time.

- In-world time progression changes the world in believable ways.

- Backstage Updates are relevant, not random.

- The user can correct memory/canon issues.

- The experience feels like a persistent world, not a chat transcript.

## Failure Criteria

The PoC fails if:

- entities forget important shared history

- entities know things they should not know

- relationships reset without reason

- unrelated events pollute entity memory

- in-world time jumps do not affect anything meaningful

- Backstage Updates feel random or generic

- the user cannot correct wrong world memory

- the world feels like disconnected chat scenes

## PoC Product Boundary

The PoC should prove depth, not breadth.

It is better to have one small world that feels coherent than a large world that feels shallow.

It is better to have 5 meaningful entities than 100 disposable ones.

It is better to prove one strong memory/backstage loop than many weak features.

## PoC Success Statement

The PoC is successful when a user can say:

This world remembers what matters.

The people/entities inside it have their own context.

Time changed things.

The world did not become confused.

I can return to it and still believe in it.
